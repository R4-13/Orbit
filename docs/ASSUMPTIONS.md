## Phase 3 — Auth & RBAC-Enforcement

| # | Annahme | Begründung |
|---|---------|------------|
| 24 | Stateless JWT: Rollen/Permissions werden beim Login/Refresh in den Access-Token eingebettet, nicht bei jedem Request aus der DB nachgeladen | Vermeidet einen DB-Roundtrip pro Request. Konsequenz: Eine Permission-Änderung wirkt erst beim nächsten Token-Refresh (spätestens nach `JWT_ACCESS_TTL`, Default 15 Min), nicht sofort. Für den MVP akzeptabel; bei Bedarf später auf Kurzzeit-Caching mit Invalidierung umstellbar. |
| 25 | Refresh-Tokens: zufälliger 256-Bit-Hex-String, in der DB nur als SHA-256-Hash gespeichert (nicht Argon2) | Refresh-Tokens sind hochentropische Zufallswerte, keine Passwörter — ein langsamer Passwort-Hash (Argon2) wäre unnötiger Overhead. Rotation bei jedem `refresh()`: das alte Token wird revoked, ein neues ausgestellt (Single-Use), damit ein abgefangenes/wiederverwendetes Token erkennbar ist. |
| 26 | `POST /api/v1/tenants` (öffentliches Self-Service-Tenant-Signup) wurde NICHT implementiert; `TenantsService.bootstrapTenant()` ist nur intern (Seed-Skript, künftiges Ops-Tool) aufrufbar | Kein Self-Service-Signup im Master-Prompt/PRODUCT_CONTEXT.md erwähnt (Zielgruppe: vertriebsbegleitetes B2B-Onboarding). Ein offener, unauthentifizierter Tenant-Erstellungs-Endpoint wäre eine nicht angeforderte, sicherheitsrelevante Angriffsfläche und wurde bewusst nicht erraten. |
| 27 | `OrbitExceptionFilter` (global, `apps/api/src/common/filters/`) mappt `OrbitError`-Subklassen auf ihren deklarierten `httpStatus` + JSON-Body (`toJSON()`); alles andere (NestJS `HttpException`, unerwartete Fehler) läuft weiter über `BaseExceptionFilter` | Ohne diesen Filter wäre z. B. ein geworfener `PermissionDeniedError` (kein `HttpException`) ein unbehandelter 500-Fehler statt des korrekten 403 — erste tatsächliche Verwendung von `OrbitError` im Code (zuvor nur deklariert, nie geworfen). |
| 28 | `PrismaService` verbindet sich NICHT eager in `onModuleInit` (`$connect()` entfernt) | Prisma verbindet standardmäßig lazy bei der ersten Query. Ein eager `$connect()` hätte jeden App-Bootstrap (auch Tests, die nur `/health` aufrufen) von einer erreichbaren Postgres-Instanz abhängig gemacht — in dieser Sandbox ohne Docker wäre dann selbst der bestehende E2E-Health-Test gebrochen. |
| 29 | `packages/shared/src/duration.ts` (`parseDurationToMs`) neu ergänzt, um `JWT_REFRESH_TTL`-Strings ("7d") in ein konkretes `expiresAt`-Datum für die `RefreshToken`-Tabelle umzurechnen | `jsonwebtoken`/`@nestjs/jwt` akzeptiert solche Strings direkt für `expiresIn` (kein Parsing nötig), aber ein DB-Zeitstempel braucht einen echten Millisekunden-Offset. Bewusst ohne Abhängigkeit auf eine Library (z. B. `ms`) für eine einzelne Funktion. |
| 30 | Keine globale `JwtAuthGuard` auf Anwendungsebene; jeder Controller/jede Route, die Auth braucht, setzt explizit `@UseGuards(JwtAuthGuard, PermissionsGuard)` | Bei aktuell nur Health (öffentlich) und Auth (naturgemäß öffentlich) gibt es noch keine schützenswerten Routen. Sobald Case-/Finance-/Sales-Controller in Phase 4+ entstehen, wird diese Konvention beibehalten (explizit, auditierbar) statt einer globalen Guard + `@Public()`-Ausnahmeliste — Entscheidung kann bei Bedarf revidiert werden, wenn die Zahl geschützter Routen stark wächst. |
| 31 | Login/Refresh/Bootstrap-Service-Tests laufen ausschließlich gegen einen gemockten `PrismaService` (keine echte DB) | Wie in Phase 2: kein Docker/Postgres in dieser Sandbox verfügbar. Die Tests verifizieren die komplette Business-Logik (Passwort-Prüfung, Token-Rotation, Rollen-/Policy-Seeding) korrekt, aber ein echter End-to-End-Lauf gegen eine lebende Datenbank steht noch aus — **REQUIRES DOCKER/POSTGRES**. |

## Nachtrag — Live-Verifikation gegen echte Infrastruktur (Docker jetzt verfügbar)

Nachdem der Nutzer Docker Desktop + WSL2 lokal installiert hat, wurden Phase
1–4 erstmals live gegen eine echte Postgres/Redis/MinIO-Umgebung getestet
(`docker compose -f docker-compose.dev.yml up -d`). Dabei wurden drei
**echte, vorher unentdeckte Bugs** gefunden und behoben — keiner davon war
über `tsc --noEmit`/Jest/Vitest sichtbar, weil keines dieser Werkzeuge den
tatsächlichen Produktionslaufweg (`node dist/api/main.js`, echtes
Docker-Image, echte HTTP-Routen) durchläuft:

| # | Bug | Fund & Fix |
|---|-----|------------|
| 38 | `minio/minio:latest` auf Docker Hub liefert `pull access denied` — MinIO hat sein offizielles Image vor einiger Zeit zu `quay.io/minio/minio` verschoben, das alte Docker-Hub-Image ist deprecated/nicht mehr verfügbar | `docker-compose.yml` und `docker-compose.dev.yml` auf `quay.io/minio/minio:latest` geändert. Ohne diesen Fund wäre `docker compose up` in jeder frischen Umgebung fehlgeschlagen. |
| 39 | **Kritisch**: `node dist/api/main.js` (der reale Laufzeit-Pfad, nicht `tsc --noEmit`) konnte `@orbit/domain`, `@orbit/config`, `@orbit/shared` nicht laden — `ERR_MODULE_NOT_FOUND` beim Start. Ursache: Alle Workspace-Packages hatten `package.json#main` direkt auf `src/index.ts` gesetzt, und deren `index.ts`-Dateien re-exportieren mit erweiterungslosen relativen Pfaden (`export * from './tenant-scope'`). `tsc --noEmit`/Jest/Vitest haben das nie bemerkt, weil sie über `tsconfig.base.json`s `paths`-Mapping direkt auf die Quelle zeigten (Type-Checking) bzw. eigene TS-Transform-Pipelines nutzten (ts-jest/vitest) — beide ignorieren `package.json#main` komplett. Nur ein echter `node`-Prozess (kein Compiler/Test-Runner mit eigenem TS-Loader) nutzt Node's native Modulauflösung, die bei erweiterungslosen Imports in einem Kontext landet, der strikte ESM-Auflösung (explizite Dateiendung erforderlich) statt klassischer CJS-Auflösung erzwingt | Doppelter Fix: (1) `package.json#main`/`#types` von `packages/{shared,config,domain,agent-core,integration-core}` auf `dist/index.js`/`dist/index.d.ts` umgestellt (kompilierte, für Node ganz normal ladbare JS-Ausgabe) — NICHT für `ui`/`testing`, die nur von Next.js/Vitest gebündelt werden und nie über einen reinen `node`-Prozess laufen. (2) `paths`-Mapping komplett aus `tsconfig.base.json` entfernt — Cross-Package-Auflösung läuft jetzt einheitlich über normale `node_modules`-Symlinks (die pnpm ohnehin anlegt) + das jeweilige `package.json#main`/`#types`, für Quellcode-Pakete (ui/testing) wie für dist-Pakete gleichermaßen. Das macht auch den in ASSUMPTIONS #22 dokumentierten `rootDir`-Workaround in `packages/domain/tsconfig.json` überflüssig (zurückgesetzt auf `rootDir: "src"`), da kein Cross-Package-Quellcode mehr in dieselbe Kompilationseinheit gezogen wird. **Konsequenz für den Dev-Workflow**: `turbo.json`s `dev`-Task hat jetzt `dependsOn: ["^build"]` — `pnpm run dev` baut alle Dependency-Packages einmalig, bevor `apps/api`/`apps/web` starten. Wer eine `packages/shared`-Datei ändert, muss `pnpm run build` (oder gezielt `pnpm --filter @orbit/shared build`) erneut laufen lassen, damit `apps/api`'s Dev-Server die Änderung sieht — es gibt (noch) keinen Cross-Package-Watch-Build. Das ist Standard-Turborepo-Praxis (Pakete werden als gebaute Artefakte konsumiert), aber eine bewusste MVP-Einschränkung gegenüber "perfektem" Hot-Reload über Package-Grenzen hinweg. |
| 40 | Doppeltes `v1` in der URL: `AuthController`, `CasesController`, `TasksController`, `DocumentsController` hatten `@Controller({ path: 'v1/xyz' })` **und** die globale URI-Versionierung (`defaultVersion: '1'`, siehe main.ts) war aktiv — Ergebnis: `/api/v1/v1/auth/login` statt `/api/v1/auth/login`, jeder Aufruf der dokumentierten Route lieferte 404. `HealthController` hatte das ursprünglich korrekt mit `version: ''` umgangen, dieses Muster wurde aber für keinen der in Phase 3/4 neu geschriebenen Controller übernommen | Vereinheitlicht: **kein** Controller setzt mehr manuell `v1` in seinen `path` oder überschreibt `version`. Alle Controller (inkl. `HealthController`, jetzt konsistent) deklarieren nur ihr Ressourcen-Segment (`'health'`, `'auth'`, `'cases'`, ...); das `v1`-Präfix kommt ausschließlich aus der globalen Versionierung. Live verifiziert: `POST /api/v1/auth/login` → echtes JWT mit aus der DB geladenen Rollen/Permissions; `POST /api/v1/cases` mit Token → 201 + `CASE_CREATED`-Audit-Log-Eintrag; ohne Token → 401. |

Diese drei Funde sind ein starkes Argument dafür, `docker compose up` +
echte HTTP-Aufrufe regelmäßig auszuführen, sobald es die Umgebung erlaubt —
nicht nur Typecheck/Unit-Tests. IMPLEMENTATION_STATUS.md wurde entsprechend
von "TESTED LOCALLY" (gemockt) auf "LIVE TESTED" (echte DB, echter
HTTP-Request) aktualisiert, wo zutreffend.

## Phase 15 — Security Hardening

| # | Annahme | Begründung |
|---|---------|------------|
| 85 | Postgres Row-Level Security nutzt ein einzelnes, eingeschränktes Rollen-Setup (`orbit_app`, `NOSUPERUSER NOBYPASSRLS`, `FORCE ROW LEVEL SECURITY`) mit einer `app.bypass_rls`-Session-GUC für die wenigen echten Cross-Tenant-Fälle, statt zweier getrennter Rollen (eine pro Tenant-Kontext) | Einfacher und ausreichend: nur `AuthService` (Login/Refresh/Logout, bevor der Tenant bekannt ist) und `TenantsService.bootstrapTenant()` (Tenant existiert noch nicht) brauchen echten Cross-Tenant-Zugriff — beide sind fester, auditierbarer Code in `apps/api`, nie durch Nutzereingaben beeinflusst. `PrismaService.withRlsBypass()` bündelt das an einer Stelle. Kritische Erkenntnis dabei: die Migrations-Rolle (`orbit`, `DATABASE_URL`) ist in den offiziellen Postgres-Images **immer** Superuser — Superuser umgehen RLS unabhängig von `FORCE ROW LEVEL SECURITY` grundsätzlich. Deshalb verbindet sich die laufende App über eine komplett andere Rolle (`orbit_app`, `DATABASE_URL_APP`) als die, die Migrationen fährt — sonst wäre die gesamte RLS-Policy wirkungslose Dekoration gewesen (live mit `psql` verifiziert: mit der `orbit`-Rolle blieben alle Zeilen sichtbar trotz aktivem `FORCE ROW LEVEL SECURITY`). |
| 86 | `forTenant()` (`packages/domain/src/tenant-scope.ts`) führt jede tenant-gescopte Operation jetzt in einer eigenen interaktiven Transaktion aus, die zuerst `SELECT set_config('app.tenant_id', $1, true)` setzt (SET-LOCAL-Semantik, pro Transaktion automatisch zurückgesetzt) | Das ist der einzige sichere Weg, eine Postgres-Session-GUC pro Request zu setzen, ohne sie über Prisms Connection-Pool auf eine spätere, fremde Anfrage derselben Connection auslaufen zu lassen. Kostet einen zusätzlichen Roundtrip pro Query (BEGIN/SET/Query/COMMIT statt nur Query) — akzeptierter MVP-Tradeoff für echte Korrektheit; die Alternative (jede der Dutzenden Service-Methoden einzeln auf `$transaction()` umstellen) hätte weit mehr Code angefasst für dasselbe Ergebnis. |
| 87 | RLS-Policies gelten für 21 der 24 tenant-gescopten Tabellen — `role_permissions`, `user_roles` und `refresh_tokens` sind bewusst ausgenommen | Diese drei Tabellen haben schlicht **keine eigene `tenant_id`-Spalte** (live per `information_schema.columns` verifiziert) — sie erreichen ihren Tenant nur indirekt über `roles.tenant_id`/`users.tenant_id`. Im aktuellen Code werden sie nie mit potenziell angreifbaren Filtern direkt abgefragt (nur bei Tenant-Bootstrap über die unscoped Verbindung, oder als Teil von `AuthService` mit RLS-Bypass) — die indirekte Absicherung über die Elterntabelle reicht für den MVP. Eine Join-basierte Policy (`EXISTS (SELECT 1 FROM roles WHERE roles.id = role_permissions.role_id AND roles.tenant_id = current_setting(...))`) wäre möglich, ist aber bewusst zurückgestellt, bis eine echte direkte Abfrage dieser Tabellen existiert. |
| 88 | `docker/postgres/10-init-app-role.sh` wird über ein eigenes, gebautes Docker-Image (`docker/postgres/Dockerfile`, `RUN chmod +x`) statt per Bind-Mount in `docker-entrypoint-initdb.d/` bereitgestellt | Live-Bug gefunden: Bind-gemountete Skripte verlieren unter Windows (NTFS hat keine Unix-Rechte-Bits; Docker Desktops Bind-Mount-Bridge erfindet keine) ihr Ausführungs-Bit, wodurch der offizielle Postgres-Entrypoint das Skript stillschweigend überspringt (`ignoring /docker-entrypoint-initdb.d/*`) statt laut zu scheitern — dieses Projekt wird auf Windows entwickelt, der Bug wäre sonst unbemerkt geblieben. Das `chmod +x` während des Image-Builds (innerhalb des Linux-Image-Dateisystems) umgeht das Host-Dateisystem komplett und funktioniert plattformunabhängig. Mit einem isolierten Wegwerf-Container (frisches Volume, kein Zugriff auf die echte Dev-Datenbank) live verifiziert: Rolle wird angelegt, `ALTER DEFAULT PRIVILEGES` greift automatisch für alle danach von `prisma migrate deploy` erzeugten Tabellen. |
| 89 | CI (`ci.yml`) legt `orbit_app` über einen expliziten `psql`-Schritt an, nicht über das Docker-Image aus #88 | GitHub-Actions-`services:`-Container starten, bevor `actions/checkout` den Code ausgecheckt hat, und unterstützen kein `build:` wie docker-compose — ein Bind-Mount/Custom-Image des Init-Skripts ist dort technisch nicht möglich. Der `psql`-Schritt läuft **vor** `prisma migrate deploy`, damit `ALTER DEFAULT PRIVILEGES` bereits aktiv ist, wenn die erste Migration Tabellen anlegt — exakt dieselbe Reihenfolge-Garantie wie bei einem frischen lokalen Volume. **Nicht live gegen einen echten Runner verifiziert** (siehe ASSUMPTIONS #83), aber Schritt für Schritt identisch zu dem, was gegen die lokale Docker-Instanz bereits erfolgreich getestet wurde. |
| 90 | `DATABASE_URL_APP` bekam `&connection_limit=20` (statt Prisms Default) | Beim wiederholten Ausführen der vollen Playwright-Suite kurz nacheinander traten Timeouts auf; die naheliegende Vermutung (Verbindungs-Pool durch #86s zusätzliche Transaktionen erschöpft) wurde per `pg_stat_activity`-Monitoring während eines Testlaufs **live widerlegt** (nie mehr als 4 Verbindungen gleichzeitig, weit unter jedem Pool-Limit) — die eigentliche Ursache war ein hängender doppelter `nest start --watch`-Prozess auf Port 3001 aus einer vorherigen manuellen Testsitzung (`EADDRINUSE`, dann korrupter Watch-Rebuild), kein RLS-bedingtes Performance-Problem. `connection_limit=20` bleibt trotzdem als harmlose, sinnvolle Absicherung gesetzt (Postgres' `max_connections=100` lässt reichlich Spielraum), auch wenn es nicht die eigentliche Ursache war — echte Diagnose immer vor Performance-Tuning, nicht statt dessen. |
| 91 | `ThrottlerGuard` wird jetzt global via `APP_GUARD` angewendet; `POST /auth/login` und `/auth/refresh` bekommen zusätzlich ein eigenes, strengeres `@Throttle()`-Limit (Default: 60 Versuche/5 Minuten, konfigurierbar über `AUTH_RATE_LIMIT_MAX`/`_WINDOW_MS`) | Live entdeckt: `ThrottlerModule.forRoot(...)` war in `app.module.ts` bereits seit Phase 3 konfiguriert, aber **nirgendwo tatsächlich angewendet** — kein `APP_GUARD`, kein `@UseGuards(ThrottlerGuard)` auf irgendeinem Controller. Rate-Limiting war die ganze Zeit über wirkungslos, obwohl `RATE_LIMIT_MAX`/`_WINDOW_MS` in `.env.example` dokumentiert waren. Der App-weite Default (120/60s) ist für Login/Refresh viel zu großzügig für Brute-Force-Schutz, daher das eigene, strengere Limit dort. Der konkrete Default-Wert (60/5min statt einer strikteren, "lehrbuchmäßigen" Zahl wie 5-10/15min) wurde bewusst gegen die tatsächliche Login-Last der Phase-14-E2E-Suiten kalibriert (~15 Requests pro vollem Lauf; ein Entwickler, der die Suite zwei-, dreimal hintereinander laufen lässt, sollte keine Sicherheitsfunktion auslösen, die für Angreifer gedacht ist) — live an genau diesem Fall verifiziert (ein zu niedriger erster Versuch mit 10/60s erzeugte echte `429`-Fehler im zweiten Testlauf). Für einen echten Produktivbetrieb sollte der Wert über die Env-Variablen weiter verschärft werden. |
| 92 | `localStorage`-JWT-Session (ASSUMPTIONS #68) bleibt für den MVP bestehen — keine Migration zu httpOnly-Cookies in Phase 15 | #68 formulierte das als bedingten Kandidaten ("falls das Produkt über eine interne Demo hinausgeht"), nicht als festen Auftrag wie die RLS-Einführung ("folgt in Phase 15", unbedingt). Bleibt offener Kandidat für einen späteren Härtungs-Pass. |
| 93 | `pnpm db:reset` (`prisma migrate reset --force`) erfordert nach dem Reset ein manuelles Re-Anwenden der Rollen-/Grant-Logik aus `docker/postgres/10-init-app-role.sh`, falls der zugrundeliegende Postgres-Container (nicht nur die Datenbank) bestehen bleibt | `ALTER DEFAULT PRIVILEGES` ist an das Paar (Rolle, Schema) gebunden; `migrate reset` legt das `public`-Schema komplett neu an, wodurch die zuvor gesetzte Default-Privileges-Regel verloren geht — Tabellen, die die anschließend erneut laufenden Migrationen anlegen, wären dann nicht mehr automatisch für `orbit_app` freigegeben.
