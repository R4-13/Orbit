## Phase 1 — Lokale Verifikation (Nachtrag)

| # | Annahme | Begründung |

| 18 | Vollständiges Prisma-Schema (25 Modelle) aus PRODUCT_CONTEXT.md, ASSUMPTIONS.md und den bereits in `@orbit/shared` vorhandenen Konstanten (PERMISSIONS, ROLES, POLICY_ACTIONS, AUDIT_EVENT_TYPES) abgeleitet, da der ursprüngliche Master-Prompt (§10) nicht im Volltext im Repo vorliegt — siehe Kopfkommentar in `packages/domain/prisma/schema.prisma` für alle Einzelentscheidungen (Single-Tenant-Membership pro User, Permission-/Policy-Action-Strings bewusst nicht als DB-Enum, AuditLog ohne FK auf User, `Decimal(14,2)` für Geldbeträge). |

| 20 | Initiale Migration (`packages/domain/prisma/migrations/20260921074619_init/`) wurde ohne laufende Postgres-Instanz per `prisma migrate diff --from-empty --to-schema-datamodel ... --script` erzeugt, nicht per `prisma migrate dev` | In dieser Sandbox ist weder Docker noch ein lokaler Postgres-Server verfügbar. `prisma migrate diff` berechnet die SQL-Differenz rein aus dem Schema (keine Live-DB nötig) und erzeugt exakt dieselbe SQL wie `migrate dev` würde. Die Migration wurde manuell in die von Prisma erwartete Ordnerstruktur (`migration.sql` + `migration_lock.toml`) gelegt. **Echter Blocker**: Ein tatsächlicher Lauf gegen eine lebende Datenbank (`prisma migrate dev`/`deploy`, inkl. Verifikation von Constraints/Indizes zur Laufzeit) steht noch aus und muss nachgeholt werden, sobald Docker verfügbar ist (`docker compose up -d postgres && pnpm prisma:migrate`). Die CI-Pipeline (`.github/workflows/ci.yml`) hat einen echten Postgres-Service-Container und führt `pnpm prisma:deploy` aus — dort wird die Migration erstmals live getestet. |
| 21 | `packages/domain/src/tenant-scope.ts`: Tenant-Isolation als Prisma-Client-Extension (`$extends` mit `query.$allModels.$allOperations`), die bei jedem tenant-gebundenen Modell automatisch `where.tenantId`/`data.tenantId` erzwingt und bei Fremd-Tenant-Zugriff `TenantIsolationViolationError` wirft | Erste konkrete Verwendung von `TenantIsolationViolationError` (bis dahin ungenutzt in `@orbit/shared`). Rein anwendungsseitige Verteidigungslinie (siehe #18); Postgres-RLS folgt in Phase 15. `TENANT_SCOPED_MODELS` ist eine explizite Liste statt Laufzeit-Introspektion über `Prisma.dmmf`, da der generierte Client in Prisma 6.19 `dmmf` nicht öffentlich exportiert (`Prisma.ModelName` hingegen schon — wird in `tenant-scope.spec.ts` genutzt, um die Liste gegen alle tatsächlich generierten Modelle abzugleichen). |
| 22 | `packages/domain/tsconfig.json`: `rootDir: "src"` entfernt (nur noch `outDir: "dist"`) | Sobald `@orbit/domain` Quellcode aus `@orbit/shared` importiert (path-gemappt auf dessen `src/`, nicht `dist/` — siehe `tsconfig.base.json`), bricht `tsc` mit TS6059 ("File is not under rootDir"), weil die eingebundene Fremd-Package-Quelle außerhalb von `domain/src` liegt. Da kein Konsument in diesem Monorepo `packages/*/dist` tatsächlich importiert (jedes Package zeigt in `package.json` mit `"main"/"types"` direkt auf `src/index.ts`), ist der exakte `dist/`-Ordnerbaum irrelevant; die gleiche Anpassung wird für `agent-core`/`integration-core` nötig, sobald auch sie paketübergreifend importieren. **Vorsicht bei zukünftigen tsc-Builds mit fehlerhafter `rootDir`-Konfiguration**: Ein fehlgeschlagener Zwischenstand dieser Änderung hat einmalig kompilierte `.js`/`.d.ts`-Dateien direkt in `packages/shared/src/` geschrieben (da `noEmitOnError` nicht gesetzt ist, emittiert `tsc` trotz TS6059-Fehlern) — wurden entfernt; `dist/`-Ordner sind über `.gitignore` ohnehin ausgeschlossen. |
| 23 | CI-Bug behoben: `.github/workflows/ci.yml` rief `pnpm prisma:migrate deploy \|\| true` auf | `prisma:migrate` ist als `prisma migrate dev` definiert (interaktiv, für lokale Entwicklung) — `deploy` wurde als zusätzliches, von `prisma migrate dev` nicht unterstütztes CLI-Argument angehängt, und `\|\| true` hätte jeden Fehler (auch einen echten Migrations-Fehler) stillschweigend verschluckt. Ersetzt durch einen neuen `prisma:deploy`-Root-Script, der `prisma migrate deploy` (den für CI/Produktion vorgesehenen, nicht-interaktiven Befehl) aufruft, ohne Fehler zu unterdrücken. |

## Phase 3 — Auth & RBAC-Enforcement

| # | Annahme | Begründung |
|---|---------|------------|
| 24 | Stateless JWT: Rollen/Permissions werden beim Login/Refresh in den Access-Token eingebettet, nicht bei jedem Request aus der DB nachgeladen | Vermeidet einen DB-Roundtrip pro Request. Konsequenz: Eine Permission-Änderung wirkt erst beim nächsten Token-Refresh (spätestens nach `JWT_ACCESS_TTL`, Default 15 Min), nicht sofort. Für den MVP akzeptabel; bei Bedarf später auf Kurzzeit-Caching mit Invalidierung umstellbar. |
| 25 | Refresh-Tokens: zufälliger 256-Bit-Hex-String, in der DB nur als SHA-256-Hash gespeichert (nicht Argon2) | Refresh-Tokens sind hochentropische Zufallswerte, keine Passwörter — ein langsamer Passwort-Hash (Argon2) wäre unnötiger Overhead. Rotation bei jedem `refresh()`: das alte Token wird revoked, ein neues ausgestellt (Single-Use), damit ein abgefangenes/wiederverwendetes Token erkennbar ist. |
| 26 | `POST /api/v1/tenants` (öffentliches Self-Service-Tenant-Signup) wurde NICHT implementiert; `TenantsService.bootstrapTenant()` ist nur intern (Seed-Skript, künftiges Ops-Tool) aufrufbar | Kein Self-Service-Signup im Master-Prompt/PRODUCT_CONTEXT.md erwähnt (Zielgruppe: vertriebsbegleitetes B2B-Onboarding). Ein offener, unauthentifizierter Tenant-Erstellungs-Endpoint wäre eine nicht angeforderte, sicherheitsrelevante Angriffsfläche und wurde bewusst nicht erraten. |
| 27 | `OrbitExceptionFilter` (global, `apps/api/src/common/filters/`) mappt `OrbitError`-Subklassen auf ihren deklarierten `httpStatus` + JSON-Body (`toJSON()`); alles andere (NestJS `HttpException`, unerwartete Fehler) läuft weiter über `BaseExceptionFilter` | Ohne diesen Filter wäre z. B. ein geworfener `PermissionDeniedError` (kein `HttpException`) ein unbehandelter 500-Fehler statt des korrekten 403 — erste tatsächliche Verwendung von `OrbitError` im Code (zuvor nur deklariert, nie geworfen). |
| 28 | `PrismaService` verbindet sich NICHT eager in `onModuleInit` (`$connect()` entfernt) | Prisma verbindet standardmäßig lazy bei der ersten Query. Ein eager `$connect()` hätte jeden App-Bootstrap (auch Tests, die nur `/health` aufrufen) von einer erreichbaren Postgres-Instanz abhängig gemacht — in dieser Sandbox ohne Docker wäre dann selbst der bestehende E2E-Health-Test gebrochen. |
| 29 | `packages/shared/src/duration.ts` (`parseDurationToMs`) neu ergänzt, um `JWT_REFRESH_TTL`-Strings ("7d") in ein konkretes `expiresAt`-Datum für die `RefreshToken`-Tabelle umzurechnen | `jsonwebtoken`/`@nestjs/jwt` akzeptiert solche Strings direkt für `expiresIn` (kein Parsing nötig), aber ein DB-Zeitstempel braucht einen echten Millisekunden-Offset. Bewusst ohne Abhängigkeit auf eine Library (z. B. `ms`) für eine einzelne Funktion. |
| 30 | Keine globale `JwtAuthGuard` auf Anwendungsebene; jeder Controller/jede Route, die Auth braucht, setzt explizit `@UseGuards(JwtAuthGuard, PermissionsGuard)` | Bei aktuell nur Health (öffentlich) und Auth (naturgemäß öffentlich) gibt es noch keine schützenswerten Routen. Sobald Case-/Finance-/Sales-Controller in Phase 4+ entstehen, wird diese Konvention beibehalten (explizit, auditierbar) statt einer globalen Guard + `@Public()`-Ausnahmeliste — Entscheidung kann bei Bedarf revidiert werden, wenn die Zahl geschützter Routen stark wächst. |
| 31 | Login/Refresh/Bootstrap-Service-Tests laufen ausschließlich gegen einen gemockten `PrismaService` (keine echte DB) | Wie in Phase 2: kein Docker/Postgres in dieser Sandbox verfügbar. Die Tests verifizieren die komplette Business-Logik (Passwort-Prüfung, Token-Rotation, Rollen-/Policy-Seeding) korrekt, aber ein echter End-to-End-Lauf gegen eine lebende Datenbank steht noch aus — **REQUIRES DOCKER/POSTGRES**. |
